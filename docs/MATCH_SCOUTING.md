# 2026 match scouting

The capture route is assignment based: `/events/[eventKey]/scout/match/[assignmentId]`. The server resolves the assignment and checks the verified account before rendering the form. An assigned scout may capture their own robot; strategy/admin can use an explicit lead override. The override records the actor separately and never changes the assignment owner.

The current `2026-rebuilt` version 2 module is the source of truth. The form uses its Zod schema directly and submits `game_slug = 2026-rebuilt`, `schema_version = 2`. It does not recreate the earlier shuffle-only model. Auto captures estimated FUEL, start position, execution result, additional-FUEL observation, and the module's small climb object. Teleop captures estimated FUEL and a single current activity state from scoring, shuttling/passing, defending, or other/idle. Transitions are kept in the final JSONB payload and never written as click telemetry. Post-match captures the revised observed role, reliability, FUEL confidence, conditional defense effectiveness, observed issues, supporting recovery/driver/climb fields, and an optional note. No cycler role, separate shuffle button, cycle count, shot percentage, BPS, intake timing, or climb timer is shown.

Auto and Teleop use immediate +1/+5/+10/+20 counters with one-tap undo. Teleop lays out the FUEL controls and four activity controls together on tablet landscape; portrait remains a short tap-and-scroll surface with the live controls grouped at the top. The active activity state is marked with `aria-pressed`, a filled accent treatment, and an ACTIVE label. The issue sheet records observed symptoms and returns to the same live state without closing or rewriting its current activity.

Drafts are local to the signed-in scout, assignment, match, and team. A client UUID is created once and retained through reloads and retries. Every meaningful edit writes the draft to IndexedDB; a before-unload guard, online/offline status, backup download, recovery screen, and revision checks protect the work. Existing localStorage drafts migrate safely. Recovery validates the typed draft, identity, FUEL undo history, activity ordering, issue IDs, and module payload before showing it. If device-clock or sleep behavior makes activity timing unsafe, the draft is blocked and the scout may explicitly omit timing as unknown; the app never fabricates durations. DNS explicitly clears field estimates and timing to unknown. Very uncertain FUEL confidence never blocks submission.

The server reparses the complete payload with the registered module before writing. It uses a service-role-only, narrowly scoped Supabase function to lock the event and assignment, verify active profile/role, compare assignment identity, reject reviewer-only causes, and insert a final submission. A final insert advances the assignment to submitted in the same transaction. `client_submission_id` makes an identical retry return the existing row; changing content under an existing UUID is rejected. The assignment is not shown as submitted until the RPC succeeds. Failed submissions leave the local draft intact.

Migration `20260930000000_match_capture.sql` adds `submitted_by_user_id`, revokes direct authenticated submission writes, and adds `start_match_capture`/`submit_match_capture` service-role functions. The existing RLS policies remain the read boundary: scouts read their own records, strategy/admin can analyze visible event data, and no client receives the service key. Confirmed root causes are deliberately deferred to a later strategy/admin correction workflow and require evidence provenance in the module schema.

The successful return URL is the event schedule with `submitted=1`; the schedule highlights its Next card. [Offline final queueing](OFFLINE_SCOUTING.md) is implemented: Submit commits locally, automatic retries use bounded backoff, and the form navigates only after server confirmation. Realtime assignment changes and the complete match correction UI remain later work.
