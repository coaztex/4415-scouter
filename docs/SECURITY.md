# Security model and deployment audit

Audit date: 2026-10-03. Scope: application source, SQL migrations applied to a fresh disposable PostgreSQL 17 database, a read-only schema dump of the linked Supabase project, generated browser assets, tests, and npm dependencies. Live Auth settings, deployment firewall, and Git history were not verified.

## Identity and roles

Supabase Auth verifies passwords. Protected server paths call `getUser()` and then read the current active `profiles` row. The app roles are `scout`, `strategy`, and `admin`; higher roles inherit lower access. The navigation is presentation only. Server actions recheck roles, and database RLS or narrow RPCs enforce data access. The service-role key bypasses RLS, so privileged clients stay in server-only modules and are called only after a role check or from a verified webhook. [Supabase explains the grant, RLS, and service-role boundaries](https://supabase.com/docs/guides/database/postgres/row-level-security).

The linked project has 26 public tables. Every public table has RLS enabled. The two internal TBA refresh/verification tables deliberately have no authenticated policy and no authenticated grants. All other public tables have policies. A broad anonymous grant on the coverage-signal table is ineffective under its RLS policy but will be revoked by the pending hardening migration; after that migration, anonymous clients have no public table grants. Ordinary authenticated users have no direct update grant on profiles, assignments, match submissions, or pit submissions. Scout final submissions are immutable through the capture APIs; strategy/admin corrections use service-only RPCs with an append-only snapshot of the prior revision. An administrator cannot bypass that final-submission guard with an ordinary authenticated table update.

Scouts can read event roster and public match context plus their own assignments and submissions. Strategy can read all active-event scouting work and use scheduling, notes, match prep, incident review, picklists, and Data Review. Admin can manage accounts and event configuration. Archived events are visible to admins; normal event read policies require an active event. This is a single-team trust model. It does not isolate multiple organizations sharing one Supabase project.

## Secrets and browser boundary

`NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` are intentionally public. `SUPABASE_SERVICE_ROLE_KEY`, `TBA_AUTH_KEY`, and `TBA_WEBHOOK_SECRET` are server-only environment values. The first two configured local private values were absent from the generated `.next/static` browser assets in this audit. The webhook secret was not configured locally, so its value could not be scanned; its references are confined to server files. There is no application import of `OPENAI_API_KEY`; `supabase/config.toml` only contains an `env(OPENAI_API_KEY)` reference for local Supabase configuration. Never add a private value to a `NEXT_PUBLIC_` variable.

`.env.local` is ignored. This workspace has no `.git` directory, so Git history and whether a secret was ever committed **cannot be verified here**. Before deployment, audit the real repository history with a secret scanner, including all branches and tags. If a credential is found, rotate/revoke it at its provider and invalidate affected sessions or tokens; removing a file from the latest commit does not undo exposure.

## Request and data boundaries

Admin server actions explicitly require `admin`; strategy actions explicitly require `strategy`. Server-side Zod parsing or equivalent field validation is used for form and JSON input. Event keys, team numbers, assignment IDs, and submission IDs are checked against the authenticated database context and, for capture/correction, rechecked inside locked RPCs. Supabase query builders parameterize values. Migration dynamic SQL uses fixed table names with identifier quoting; no request-controlled SQL text is executed.

React renders scout notes as text. The source has no `dangerouslySetInnerHTML`, `innerHTML`, `eval`, or `new Function` path for submitted content. External robot-image URLs are allowlisted to the expected TBA image host. User photo uploads require an active account and event/team membership, a same-origin request, a bounded multipart body, supported image content, a 12 MB input limit, 40-million-pixel decode cap, and a resized JPEG of at most 2 MB. The two Storage buckets are private with MIME/size constraints; local migrations grant authenticated users only object reads tied to event-visible metadata. No authenticated Storage write/delete policy is created. The server performs controlled uploads/deletes using its service credential. [Supabase Storage applies RLS to object access](https://supabase.com/docs/guides/storage/security/access-control).

Username login resolves the Auth email on the server and returns one generic failure for missing usernames, wrong passwords, and disabled accounts. Correct pending-account credentials allow only the pending-approval state. It performs a failed password check for a missing username to reduce an obvious timing split. It has a 10-attempt-per-minute, per-process burst limit and uses Supabase Auth limits; this is not a distributed guarantee. Login does not expose the email or raw provider errors. The TBA webhook checks HMAC-SHA256 over the original request bytes with a timing-safe comparison, limits the body to 256 KB, and uses a database lease to limit refreshes. Scouting sync requires an active account, matching author, same-origin request, a 500 KB body limit, validated payload, and idempotent client submission ID. Next.js Server Actions also compare request origin and host ([Next.js documentation](https://nextjs.org/docs/app/api-reference/config/next-config-js/serverActions)).

## Admin bootstrap and recovery

For a fresh deployment, enable Email signup, disable Confirm email, and keep anonymous sign-in disabled. New profiles are pending inactive Scouts; they receive no application access before admin approval. Supabase then marks the email confirmed without verifying mailbox ownership, so an administrator must verify identity and team membership independently. See [AUTHENTICATION_UX.md](AUTHENTICATION_UX.md) for the current setup. Create the first administrator in the Supabase Dashboard with a strong password; use the one-time guarded SQL transaction in [ADMIN_BOOTSTRAP.md](ADMIN_BOOTSTRAP.md) to promote that exact UUID only when no active admin exists. Normal later approval/provisioning runs through Admin → Users and the audited `admin_save_profile` RPC. The database guard prevents deactivating or demoting the last active admin.

If an administrator loses a password and another active admin exists, that admin can resolve a reset request in Users. The last active admin is protected against reset because it would temporarily deactivate the account. If no usable admin remains, a trusted project operator must inspect Auth, profile, and audit rows before a targeted Dashboard recovery. Do not disable RLS, remove the last-admin guard, create a public bootstrap endpoint, or place credentials in chat or source control.

## Findings and deployment checks

- Fixed in source and the pending migration during this audit: bounded streaming reads for sync and webhook requests, bounded multipart reads plus a same-origin check for photo uploads, a pit-submission correction trigger that previously referenced match-only fields, a broad grant on the coverage-signal table, and obsolete direct-submission write policies. The database fixes are migration `20261014000000_security_hardening.sql`.
- `npm audit --omit=dev` reports zero vulnerabilities. Full `npm audit` reports five high-severity advisories through the development-only `eslint-config-next → fast-glob → micromatch → braces` chain. npm currently offers only a major, incompatible downgrade as its automatic fix. No major dependency change was made; review this tooling advisory when a compatible patch is available.
- The linked project's read-only dump shows 26/26 public tables with RLS, 24 tables with scoped policies, two internal TBA tables with no client policies/grants, and only two Storage object policies, both for authenticated SELECT. No Storage object write policy was found. The migration list shows Data Review (`20261013000000`) applied and security hardening (`20261014000000`) pending. Apply the latter before deployment and recheck for Dashboard-created drift.
- Verify public signup is enabled for pending team approval, Confirm email is disabled, anonymous sign-in is disabled, the production login endpoint has a deployment-wide rate limit, and private variables are configured only in the server environment. The in-process login limiter and authenticated sync guards do not replace host-level abuse controls.
- Audit Git history from a checkout that contains `.git`. The current workspace cannot satisfy this history check.
